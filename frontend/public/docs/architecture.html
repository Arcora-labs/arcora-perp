Architecture

Arcora Perp is an application-specific rollup: a TEE gives millisecond matching and privacy, a zkVM proof makes every settlement verifiable, and Base Sepolia holds custody. This page walks the full pipeline.

The settlement pipeline

1

Matching in a TEE milliseconds

The order-matching engine and sequencer run inside an Azure TDX confidential VM (Intel TDX). The enclave identity is attestation-bound: a DCAP quote with the measurement pinned at boot (TCB UpToDate). Orders are matched off-chain in milliseconds on a price-time-priority book.

2

Signed receipts — soft finality milliseconds

Every accepted order returns an enclave-signed receipt (secp256k1, recovering to the enclave signer). The receipt doubles as an inclusion proof the user can later wield in the on-chain challenge game. Order states: ACCEPTED → MATCHED (filled, soft) → SETTLED (hard).

3

Windowed sealing

The sequencer seals trading activity into windows. A window is the unit of proving: all fills, funding payments, liquidations, ADL events, deposits, and withdrawals that happened since the last settled root.

4

SP1 zkVM re-execution ~10–20 min

For each window, an SP1 zkVM proof re-executes the entire engine transition from the previous state root to the new one. All six commitment roots — state, manifest, ordered, withdrawals, rejected, plus the commitment — are derived inside the zk guest from the replayed operations, never trusted from the operator.

5

Groth16 verification on-chain

The SP1 proof is wrapped into a Groth16 proof and verified by SP1ZkVerifier inside DarkPerpSettlement.settleBatch on Base Sepolia. The contract enforces previous-root continuity — the operator cannot settle a state transition the proof doesn't attest.

6

Merkle withdrawals

USDC sits in CollateralVault. Withdrawals are recorded off-chain, included in the window's withdrawals Merkle root, and once the window settles, anyone can execute claim(to, amount, nonce, root, proof) permissionlessly — funds can only go to the leaf-bound address, and any historically published root stays claimable (a later root can never strand a withdrawal).

Challenge game, bonding, liveness

The zk proof makes settled state unforgeable, but a malicious operator could still try to drop orders it accepted. The challenge game closes that hole:

  • Operator bond. The operator posts a USDC bond with a floor of 5% of vault TVL (requiredBond(), BOND_BPS = 500).
  • Inclusion challenges. Anyone holding an enclave-signed receipt can open an on-chain inclusion challenge against a settled window. Challenges are themselves bonded at 0.01 ETH to prevent griefing, with a 300-block challenge window to answer.
  • Slashing. If the sequencer cannot prove that the receipt's order was included in a settled window, the operator's bond is slashed to the challenger (pull-payment).
  • Liveness / forced exit. If the sequencer stops settling for 7,200 blocks, the system enters forced-exit / close-only mode. The settled state remains withdrawable — an offline operator can halt trading, but cannot trap settled funds.

Privacy layer

Sealed order ingress

Order terms are encrypted in the browser to the enclave's rotating X25519 epoch key using a sealed box: X25519 ECDH → HKDF-SHA256 → XChaCha20-Poly1305, wire format 0x01 ‖ epk ‖ nonce24 ‖ ct. The HTTP body carries only {epochId, sealed} — no plaintext trade terms on the wire (TLS on top). The epoch key is served signed by the enclave identity (GET /v1/enclave/epoch) so clients verify before sealing, and the AAD binds each ciphertext to (epoch ‖ account owner), ruling out cross-account replay. In production posture, unsealed orders are refused. Full byte-level detail: sealed order wire format.

Shielded balances

Account state lives as encrypted notes. The public can see aggregate book depth — enough to trade against — but not per-account balances or positions.

Encrypted order log & unlinkable ADL

The order log is encrypted, and ADL haircut receipts are unlinkable to third parties: outsiders cannot reconstruct who was deleveraged or map order flow to accounts.

Crash safety

The enclave is designed to fail without losing or corrupting state:

  • Sealed snapshots. State snapshots are encrypt-then-MAC'd under the enclave seed — readable and verifiable only by an enclave with the right measurement.
  • Rollback journal (WAL). The in-flight settle window is covered by a sealed write-ahead journal. A restart mid-settle self-recovers at boot: the sequencer rolls the window back or forward, reconciled against what actually landed on-chain.
  • This path is verified live with a restart-during-proof drill on the running testnet.

Trust boundaries, summarized

PropertySecured by
Settled state transitions (fills, funding, liquidations, ADL, balances)SP1 zkVM proof, Groth16-verified on-chain
Withdrawals from settled statePermissionless Merkle claims against the vault
Order inclusion (accepted orders make it into windows)Signed receipts + bonded challenge game
Matching integrity & privacy before settlementIntel TDX attestation (enclave identity sealed to the measurement)
Funds safety if the operator disappearsLiveness timeout → forced-exit / close-only on settled state
